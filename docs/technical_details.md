## 1. 背景知识：Wallpaper Engine 是怎么存储壁纸的？

当你在 Steam 创意工坊订阅一张 Wallpaper Engine 壁纸后，Steam 会将壁纸下载到本地。这些壁纸统一存放在：

```
Steam/steamapps/workshop/content/431960/
├── 123456789/          ← 壁纸A（Workshop ID 作为文件夹名）
│   ├── project.json    ← 壁纸元数据（标题、作者、预览图...）
│   ├── scene.json      ← 场景配置
│   ├── scene.pkg       ← 📦 核心资源打包文件
│   └── preview.jpg     ← 预览图
├── 987654321/          ← 壁纸B
│   ├── project.json
│   ├── scene.mp4       ← 视频壁纸，直接就是 mp4
│   └── preview.jpg
└── ...
```

### 壁纸的三种类型

| 类型 | 特征 | LianPkg 处理方式 |
|------|------|-----------------|
| **场景壁纸 (Scene)** | 包含 `.pkg` 文件，内含 3D 模型、纹理、着色器等 | 解包 PKG → 转换 TEX → 输出 PNG |
| **视频壁纸 (Video)** | 直接包含 `.mp4` 文件 | 直接复制 |
| **网页壁纸 (Web)** | 包含 `index.html` | 直接复制 |

**LianPkg 的核心价值**在于处理**场景壁纸**——这类壁纸的素材被锁在 `.pkg` 压缩包里，其中的纹理又使用了专有的 `.tex` 格式，普通用户无法直接查看。

### `project.json` 都记录了什么？

每个壁纸目录下都有一个 `project.json`，它是壁纸的"身份证"：

```json
{
    "title": "星空少女",
    "type": "scene",
    "preview": "preview.jpg",
    "tags": ["Anime", "Girls"],
    "workshopid": "123456789",
    "description": "A beautiful starry night wallpaper"
}
```

LianPkg 通过读取 `type` 字段判断壁纸类型，通过 `title` 显示壁纸名称。

## 2. PKG 格式完全解析

`.pkg` 是 Wallpaper Engine 自创的归档格式。你可以把它理解为一个**极其简化的 ZIP 文件**——它没有压缩，只是把很多小文件"粘贴"在一起，并在前面加了一个"目录"。

### 2.1 文件的物理布局

一个 `.pkg` 文件从头到尾长这样：

```
┌─────────────────────────────────────────────────────┐
│  区域 1: 包头 (Header)                               
│  ┌──────────────────────────────────────────┐     
│  │ [4字节] 版本字符串长度 = 4                     
│  │ [4字节] 版本字符串 = "PKG0"                    
│  │ [4字节] 文件总数量 = N                           
│  └──────────────────────────────────────────┘     
│                                           
│  区域 2: 索引表 (Index Table) — 共 N 条           
│  ┌──────────────────────────────────────────┐     
│  │ 条目 #1:                              
│  │   [4字节] 文件名长度                     
│  │   [?字节] 文件名 (UTF-8)                 
│  │   [4字节] 数据偏移量 (相对于数据区起始)    
│  │   [4字节] 数据大小 (字节)                  
│  │                                         
│  │ 条目 #2: ...                             
│  │ ...                                     
│  │ 条目 #N: ...                             
│  └──────────────────────────────────────────┘    
│                                                    
│  区域 3: 数据区 (Data Block) ← 从此位置开始         
│  ┌──────────────────────────────────────────┐    
│  │ [文件1的二进制数据]                   
│  │ [文件2的二进制数据]                     
│  │ ...                                    
│  │ [文件N的二进制数据]                      
│  └──────────────────────────────────────────┘       
└─────────────────────────────────────────────────────┘
```

### 2.2 逐步解包过程

让我们用一个具体的例子来看解包过程。假设有个 `scene.pkg`，里面包含 3 个文件：

#### 第一步：读取包头

```
偏移 0x00: [04 00 00 00]  ← 版本字符串长度 = 4
偏移 0x04: [50 4B 47 30]  ← "PKG0" (ASCII)
偏移 0x08: [03 00 00 00]  ← 文件数量 = 3
```

> 所有整数均为**小端序 (Little-Endian)**。`03 00 00 00` 在小端序下 = 3。

#### 第二步：读取索引表

接下来连续读取 3 个条目：

| # | 文件名 | 偏移量 | 大小 |
|---|--------|--------|------|
| 1 | `materials/wall.tex` | 0 | 65536 |
| 2 | `materials/floor.tex` | 65536 | 32768 |
| 3 | `scene.json` | 98304 | 1024 |

每个条目的读取方式：
1. 读 4 字节得到名称长度 L
2. 读 L 字节得到文件名字符串 
3. 读 4 字节得到该文件在数据区中的起始偏移
4. 读 4 字节得到该文件的数据长度

#### 第三步：提取文件

索引表读完后，我们记下当前读指针位置，这就是**数据区的起点**（`data_start`）。

对于每个条目，计算：
```
实际位置 = data_start + 条目的偏移量
```

然后从 PKG 文件中截取 `实际位置` 到 `实际位置 + 大小` 这一段数据，写入磁盘即可。

```
data_start + 0      → 取 65536 字节 → 写入 materials/wall.tex
data_start + 65536  → 取 32768 字节 → 写入 materials/floor.tex  
data_start + 98304  → 取 1024  字节 → 写入 scene.json
```

### 2.3 LianPkg 中的实现

LianPkg 使用自定义的 `Reader` 结构体（`src/core/pkg/utl.rs`）来读取二进制数据：

```rust
// 读取 4 字节小端序整数
let file_count = reader.read_u32();

// 读取长度前缀字符串（先读4字节长度，再读对应数量的字节）
let name = reader.read_string();  
```

核心解包流程在 `src/core/pkg/unpack.rs` 中，大约 90 行代码完成全部工作。

## 3. TEX 格式完全解析

`.tex` 是整个项目中最复杂的部分。它是 Wallpaper Engine 专用的纹理容器格式，可以存储多种不同编码的图像数据。

### 3.1 TEX 文件的完整结构

```
┌───────────────────────────────────────────────────────────────┐
│  层级 1: 文件签名 (Magic Bytes)                               
│  ┌───────────────────────────────────────────────────┐      
│  │ [16字节] "TEXV0005" + 填充零字节                          
│  │ [16字节] "TEXI0001" + 填充零字节                          
│  └───────────────────────────────────────────────────┘     
│                                                              
│  层级 2: 文件头 (TexHeader) — 28 字节                       
│  ┌───────────────────────────────────────────────────┐
│  │ [4字节] format    — 纹理格式编码 (0/4/6/7/8/9)           
│  │ [4字节] flags     — 标志位 (bit5=视频)                 
│  │ [4字节] texture_width  — 纹理宽度                     
│  │ [4字节] texture_height — 纹理高度                     
│  │ [4字节] image_width    — 图像宽度                       
│  │ [4字节] image_height   — 图像高度                       
│  │ [4字节] unk_int0       — 未知字段                      
│  └───────────────────────────────────────────────────┘
│                                                             
│  层级 3: 图像容器 (TEXB)                                     
│  ┌───────────────────────────────────────────────────┐
│  │ [16字节] Magic — "TEXB0001"~"TEXB0004"                
│  │ [4字节]  image_count — 图像数量                        
│  │ [4字节]  image_format  (仅 TEXB0003+)            
│  │ [4字节]  is_video_mp4  (仅 TEXB0004)         
│  │                                                  
│  │  ┌─ 图像 #1 ───────────────────────────────────┐
│  │  │ [4字节] mipmap_count                      
│  │  │  ┌─ Mipmap #0 (最高清晰度) ──────────┐
│  │  │  │ [4字节] width                     
│  │  │  │ [4字节] height                    
│  │  │  │ [4字节] is_lz4_compressed (V2+)     
│  │  │  │ [4字节] decompressed_size (V2+)      
│  │  │  │ [4字节] byte_count                  
│  │  │  │ [?字节] 图像数据                     
│  │  │  └─────────────────────────────────┘
│  │  │  ┌─ Mipmap #1 (缩小版) ─────────────┐  
│  │  │  │ ...（更小尺寸）                 
│  │  │  └─────────────────────────────────┘    
│  │  └────────────────────────────────────────────┘
│  └───────────────────────────────────────────────────┘
└───────────────────────────────────────────────────────────────┘
```

### 3.2 什么是 Mipmap？

**Mipmap** 是同一张图片的不同分辨率版本。游戏引擎在渲染时，远处的物体使用低分辨率版本，近处使用高分辨率版本，以提高性能。

```
Mipmap #0: 1024×1024  ← 我们要提取的（最清晰）
Mipmap #1:  512×512
Mipmap #2:  256×256
Mipmap #3:  128×128
...
```

**LianPkg 只提取 Mipmap #0**——即最高清晰度的那一层。

### 3.3 TEXB 版本差异

不同版本的 TEXB 容器记录的信息不同：

| 版本 | image_format | is_video | LZ4 压缩 | 说明 |
|------|-------------|----------|----------|------|
| TEXB0001 | ✗ | ✗ | ✗ | 最早期版本，无压缩 |
| TEXB0002 | ✗ | ✗ | ✓ | 增加 LZ4 压缩支持 |
| TEXB0003 | ✓ | ✗ | ✓ | 增加图像格式字段（FreeImage 枚举） |
| TEXB0004 | ✓ | ✓ | ✓ | 增加 MP4 视频支持 |

### 3.4 格式判定的优先级逻辑

TEX 文件中存在多个可能指示格式的字段，LianPkg 按以下优先级判定：

```
优先级 1: 是视频吗？
    → flags 的 bit5 (& 32) 为 1   → MP4 视频
    → is_video_mp4 字段为 true     → MP4 视频

优先级 2: 是否有嵌入的常见图片格式？
    → image_format >= 0 时，查表转换：
        0  → BMP        2  → JPEG      13 → PNG
        25 → GIF       ...（共 35 种 FreeImage 格式）

优先级 3: 回退到 header.format（GPU 纹理格式）
    → 0  → RGBA8888（未压缩原始像素）
    → 4  → DXT5（BC3，带完整 Alpha 通道）
    → 6  → DXT3（BC2，简单 Alpha）
    → 7  → DXT1（BC1，无/1bit Alpha）
    → 8  → RG88（双通道：法线贴图常用）
    → 9  → R8（单通道：灰度/遮罩图）
```

### 3.5 数据是怎么被压缩的？

TEX 中的图像数据可能经过 **LZ4** 压缩。LZ4 是一种极其快速的无损压缩算法，解压速度可达数 GB/s。

读取流程：
```
if is_lz4_compressed:
    compressed_data = 读取 byte_count 字节
    raw_data = LZ4解压(compressed_data, decompressed_bytes_count)
else:
    raw_data = 读取 byte_count 字节
```

### 3.6 GPU 纹理解码

当数据是 DXT/BC 格式时，它存储的不是人眼可读的像素，而是 GPU 直接使用的压缩块。每种格式的原理：

#### DXT1 (BC1) — 最紧凑的压缩

每 4×4 像素块压缩为 8 字节。存储 2 个基准颜色 + 16 个 2-bit 索引。
- 压缩比：6:1（RGB）
- 适用：不需要透明度的纹理

#### DXT3 (BC2) — 简单透明度

每 4×4 像素块 = 16 字节。颜色部分同 DXT1，额外 8 字节存储每像素 4-bit Alpha 值。
- 适用：透明度突变的边缘（如文字、UI）

#### DXT5 (BC3) — 平滑透明度

每 4×4 像素块 = 16 字节。颜色部分同 DXT1，Alpha 通道用类似颜色的插值方式压缩。
- 适用：大多数场景纹理（渐变透明度）

#### 解码后的结果

无论原始格式是什么，解码后都统一为 **RGBA8888** 格式：
```
每个像素 = [R, G, B, A]  (各 1 字节，共 4 字节)
总数据量 = 宽 × 高 × 4 字节
```

然后使用 `image` 库编码为标准 PNG 文件保存。

### 3.7 特殊格式处理

| 检测到的格式 | 处理方式 | 输出格式 |
|-------------|---------|---------|
| MP4 视频 | 原样写入 | `.mp4` |
| PNG/JPEG/BMP/GIF | 原样写入（数据就是标准图片文件） | 对应扩展名 |
| RGBA8888 | 直接当作像素数据编码 | `.png` |
| DXT1/3/5 | GPU 纹理解码 → RGBA → 编码 | `.png` |
| RG88 | 双通道 → 补 B=0, A=255 → RGBA | `.png` |
| R8 | 单通道灰度 → 复制到 RGB, A=255 | `.png` |

## 4. LianPkg 处理流水线详解

`lianpkg auto` 命令执行以下完整流程：

```
                ┌──────────────┐
                │ Steam Workshop │
                │   /431960/     │
                └──────┬───────┘
                       │
              ┌────────▼────────┐
              │  Phase 1: 扫描   │ 读取 project.json, 分类壁纸
              └────────┬────────┘
                       │
         ┌─────────────┼─────────────┐
         ▼                           ▼
   ┌───────────┐              ┌───────────┐
   │ 无 PKG 的  │              │ 有 PKG 的  │
   │  壁纸      │              │  壁纸      │
   └─────┬─────┘              └─────┬─────┘
         │                          │
         ▼                          ▼
   ┌───────────┐              ┌───────────────┐
   │ 复制到     │              │ 直接从 Workshop│
   │ Wallpapers │             │ 读取 PKG 解包  │
   │ _Raw/      │             └───────┬───────┘
   └───────────┘                      │
                              ┌───────▼────────┐
                              │  Phase 2: 解包  │ 解析 PKG → 提取文件
                              │  → Pkg_Unpacked/│
                              └───────┬────────┘
                                      │
                              ┌───────▼────────┐
                              │  Phase 3: 转换  │ 解析 TEX → 解码 → PNG
                              │  → tex_converted/│
                              └───────┬────────┘
                                      │
                              ┌───────▼────────┐
                              │  Phase 4: 清理  │ 删除中间产物
                              │  保留最终产物     │
                              └────────────────┘
```

> 旧版中有一个 `Pkg_Temp` 中间目录用于缓存 PKG 文件副本，v2.0 已将其消除，现在直接从 Workshop 源路径读取 PKG 解包。

### 最终输出目录结构

```
~/.local/share/lianpkg/
├── Wallpapers_Raw/          ← 非 PKG 壁纸的原样副本
│   ├── 987654321/
│   │   └── scene.mp4
│   └── ...
│
└── Pkg_Unpacked/
    └── 123456789/           ← 壁纸ID
        ├── tex_converted/   ← ✨ 最终产物
        │   ├── wall.png
        │   ├── floor.png
        │   ├── project.json ← 从源目录复制的元数据
        │   └── preview.jpg
        ├── materials/       ← 解包产物（默认会被清理）
        │   ├── wall.tex
        │   └── floor.tex
        └── scene.json       ← （默认会被清理）
```

### 增量处理机制

LianPkg 在 `state.json` 中记录已处理的壁纸 ID。开启 `--incremental` 后，再次运行时会跳过已处理的壁纸，大幅缩短处理时间。

## 5. 架构设计与代码结构

```
src/
├── main.rs            ← 程序入口
├── lib.rs             ← 库入口（导出 core + api）
│
├── core/              ← 💎 纯业务逻辑层（无 I/O 假设）
│   ├── error.rs       ← 统一错误类型 CoreError
│   ├── cfg/           ← 配置文件 (TOML) 与状态文件 (JSON) 的 CRUD
│   ├── disk/          ← 磁盘空间检查
│   ├── paper/         ← 壁纸扫描、分类、复制
│   ├── path/          ← 跨平台路径解析（Linux/Windows）
│   ├── pkg/           ← PKG 文件解析与解包
│   └── tex/           ← TEX 文件解析、解码与转换
│
├── api/               ← 📡 对外接口层
│   ├── native/        ← Rust 原生 API（CLI 和 GUI 共用）
│   │   ├── context.rs ← 应用上下文与配置管理
│   │   ├── scan.rs    ← 壁纸扫描与复制
│   │   ├── auto.rs    ← 流水线 API（编排完整流程）
│   │   ├── pkg.rs     ← PKG 解包 API
│   │   ├── tex.rs     ← TEX 转换 API（rayon 多线程）
│   │   └── util.rs    ← 内部工具函数
│   └── ffi/           ← C FFI 层（供 Flutter 等调用）
│       ├── mod.rs     ← lianpkg_call / lianpkg_free_string
│       ├── dispatch.rs← action 分发器（15 种操作）
│       └── types.rs   ← 请求/响应/进度类型定义
│
└── cli/               ← 🖥️ 命令行界面层
    ├── args.rs        ← clap 参数定义
    ├── logger.rs      ← 日志控制
    ├── output.rs      ← 终端美化输出
    └── handlers/      ← 各子命令处理器
        ├── auto.rs    ← lianpkg auto
        ├── wallpaper.rs← lianpkg wallpaper
        ├── pkg.rs     ← lianpkg pkg
        ├── tex.rs     ← lianpkg tex
        ├── config.rs  ← lianpkg config
        └── status.rs  ← lianpkg status
```

### 三层架构的设计思想

```
CLI (handlers/)  ──调用──▶  API (native/)  ──调用──▶  Core (core/)
   用户交互              高级接口封装            纯业务逻辑
   参数解析              状态管理               文件解析
   格式化输出            流水线编排              二进制读写
```

这种分层设计意味着：
- **Core** 层可以被任何 Rust 代码复用
- **API** 层可以同时服务于 CLI 和 FFI（即 Flutter GUI）
- **CLI** 层只负责用户交互，不包含核心业务逻辑

## 6. 依赖库说明

| 库名 | 用途 | 为什么选它 |
|------|------|-----------|
| `lz4_flex` | LZ4 解压 TEX 数据 | 纯 Rust 实现，无需 C 依赖 |
| `texture2ddecoder` | DXT/BC 纹理解码 | 专门处理 GPU 纹理格式 |
| `image` | RGBA 像素 → PNG 编码 | Rust 生态标准图像库 |
| `byteorder` | 小端序二进制读取 | TEX reader 使用 |
| `rayon` | TEX 并行转换 | 充分利用多核 CPU，大幅提升批量转换速度 |
| `clap` | 命令行参数解析 | 自动生成帮助文档，支持子命令 |
| `serde` + `toml` + `serde_json` | 配置文件序列化 | Config.toml 和 State.json |
| `chrono` | ISO 8601 时间戳 | state.json 中的 processed_at / last_run |
| `human_bytes` | 人类可读字节数 | CLI 磁盘空间显示 |
| `dirs` | 跨平台目录解析 | 获取 ~/.config 等标准目录 |
| `fs2` | 磁盘空间查询 | 跨平台获取可用空间 |
| `unicode-width` | CJK 字符宽度 | 终端表格的正确对齐 |

## 7. 常见问题与疑难解答

### Q: TEX 文件解码出来的图片颜色不对？

DXT 解码器输出的像素顺序是 BGRA（而非 RGBA）在某些实现中可能不同。`texture2ddecoder` 使用 `u32` 打包像素，LianPkg 通过 `to_le_bytes()` 拆分，顺序为 `[B, G, R, A]`。在某些边缘情况下可能需要交换 R/B 通道。

### Q: 为什么有些 TEX 转换失败？

常见原因：
1. **格式不支持** — `header.format` 为未知值（MipmapFormat::Invalid）
2. **数据损坏** — LZ4 解压失败，通常意味着文件不完整
3. **尺寸不匹配** — 解码后的数据大小不等于 `width × height × 4`

### Q: PKG 内的文件名有中文会乱码吗？

PKG 使用 UTF-8 编码存储文件名。LianPkg 的 PKG Reader 使用 `String::from_utf8()`，如果遇到无效 UTF-8 会返回 `CoreError::InvalidData` 错误（不会崩溃）。TEX Reader 则使用 `from_utf8_lossy`，无效字节替换为 `�`。

### Q: 处理 1000+ 壁纸大概需要多少时间和空间？

- **时间**：取决于 PKG 数量和 TEX 解码复杂度，通常 5-30 分钟
- **空间峰值**：约为 PKG 总大小的 3.5 倍 + 原始壁纸大小（解包 ×1.5 + 转换 ×2.0 + Raw）
- **最终占用**：启用清理后，仅保留 `tex_converted` 和 `Wallpapers_Raw`
